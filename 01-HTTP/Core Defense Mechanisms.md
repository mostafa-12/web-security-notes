## Handling User Input

### Input Handling

Core Principle:
- All user input is untrusted.

Types of Input:
1. User Input
   - Text fields
   - Search
   - Comments
   - File names
   - etc.

2. Server-generated Data
   - Cookies
   - Hidden form fields
   - URL parameters generated by the server
   - etc.

Handling:

User Input:
- Don't reject it just because it looks malicious.
- Handle it safely based on where it will be used
  (DB, HTML, Files, OS, ...).

Server-generated Data:
- Never trust it after it reaches the client.
- Validate it strictly (expected values/format).
- If modified unexpectedly:
    - Reject the request.
    - Log the event.

~~~
                Input
                  │
      ┌───────────┴───────────┐
      │                       │
User Input          Server-generated Data
      │                       │
Flexible             Strict Validation
      │                       │
Handle Safely        Reject if Tampered and log it 
~~~


### Boundary Validation

Concept:
- Validate data at every trust boundary, not only at the client-server boundary.

Purpose:
- Protect each component according to its own context.

Why?
- The same input may pass through multiple components.
- Each component has different security requirements.
- Data may change during processing.

### Multistep Validation & Canonicalization

Concept:
- Multiple validation or decoding steps can introduce security bypasses.

Problems:
1. Validation order may reconstruct malicious input.
2. Decoding after validation may reveal hidden payloads.

Canonicalization:
- Convert encoded data into its normal form.
- Always validate the canonical (decoded) representation.

Takeaway:
- Validation order matters.
- Never validate encoded data and decode it afterward.
- Prefer rejecting suspicious input over complex sanitization when appropriate.

Examples:
DB      → Parameterized Queries
HTML    → HTML Encoding
XML     → XML Encoding
SMTP    → SMTP Injection Protection

### Handling Attackers

Purpose:
- Detect, monitor, and respond to malicious users.

Main Tasks:
- Handle errors safely.
- Maintain audit logs.
- Alert administrators.
- React to attacks.

Takeaway:
- Assume attackers will target the application.
- Design defenses to detect, log, and slow them down.
### Handling Errors

Purpose:
- Prevent error messages from helping attackers.

Rules:
- Handle exceptions gracefully.
- Never expose debug information or stack traces.
- Log detailed errors internally.

Risk:
- Verbose errors may reveal sensitive information or application internals.
### Audit Logs

Purpose:
- Record security-related events for investigation.

Log Important Events:
- Login success/failure.
- Password changes.
- Critical transactions.
- Blocked access attempts.
- Detected attack payloads.

Requirements:
- Include timestamp, IP, and user (if authenticated).
- Protect logs from unauthorized access.

Risk:
- Exposed logs may leak sensitive data (tokens, credentials, request data).
### Alerting Administrators

Purpose:
- Detect attacks in real time.

Common Indicators:
- Unusual request rates.
- Suspicious business activity.
- Known attack payloads.
- Modified hidden fields or cookies.

Takeaway:
- Application-specific alerts are more accurate than generic WAF rules.

### Reacting to Attacks

Purpose:
- Slow down or stop attackers after detecting malicious behavior.

Examples:
- Rate limiting.
- Delaying responses.
- Terminating sessions.
- Requiring re-authentication.

Takeaway:
- These are defense-in-depth measures, not replacements for fixing vulnerabilities.
### Managing the Application

Purpose:
- Secure administrative functionality.

Risks:
- Weak admin authentication.
- Broken access control.
- XSS in admin panel.
- Dangerous admin operations (files, OS commands).

Takeaway:
- Admin interfaces are high-value targets and require stronger protection.
